# 0077 Hardening tests for 4.0: cross-stack and end-to-end suites, accessibility with axe-core, security, privacy and resilience suites

Status: Proposed (V4, milestone M7, 2026-10-18). Owner: release area (F). Amends 0043 (Vitest projects: a `security` project is added, the `parity` project is gone, see 0066), 0039 (the pinned `axe-core` dev dependency it announced gets its version and licence note) and 0041 (new dev dependency: exact pin, reason and evidence recorded here). Relates to 0045 (local request security), 0046 (terminal-safe output), 0060 (MCP), 0072 and 0073 (language and information architecture), 0076 (release gates).
Planned for a later 4.x release.

## Context
The V3 plan reserved a phase for end-to-end, accessibility, security, privacy, isolation and resilience suites and built none of them beyond one browser smoke. V4 needs them against the finished system: a redesigned interface in two languages, an installed hooks path, backups and exports, a read-only MCP server and a bundled runtime that runs on three operating systems. Three V3 assumptions changed: there is no legacy engine to compare with (no parity suite, no legacy-parity spec), the real user settings must never be read (the V3 check SEC-24 hashed `~/.claude/settings.json`), and Linux and macOS are targets, so every suite must be platform neutral.

## Decision
1. **Layers.** Cross-package contract tests that start a real instance live in the integration project, in the package that owns the client (`packages/web/test/*.int.test.ts`): the web client is run against every route of the shared registry, the stream client against the real stream, the panel parser against the real panels. Browser tests are Playwright specs in `packages/web/e2e/specs/` that start instances through the CLI on ports 18500-18599; the layout, keyboard and language specs and the visual QA tool belong to the interface work (0073 decision 12). Security, isolation and resilience suites are Vitest projects of real processes (`tests/security`, `tests/isolation`, `tests/resilience`), run in shuffled order with three seeds by `test:stress`.
2. **Accessibility.** `axe-core` 4.14.0, exact pin, `devDependencies` of `@mcs/web` only. Component run (happy-dom, rules of WCAG 2.0 A and AA, 2.1 AA, 2.2 AA, colour contrast off because the environment cannot compute styles) over the page matrix of the interface work in both languages; browser run (contrast on) over every route in light and dark and both languages, and over the open states a static scan misses (the Live popover, the user menu, the filter popover, the column chooser, the shortcuts dialog). Zero violations are required. A rule may be excluded only through an entry with a rule id, a selector and a written reason; the list starts empty. Failure messages carry rule, impact and selectors, never page text. A negative fixture proves the scan is not idle.
3. **Security suite.** Real server, real CLI, real hook handler: Host, Origin and fetch-metadata guards, request limits and timeouts, response headers and the CSP (also on the bundled server), id and path containment including junction and symlink escapes, cleanup, export and restore path rules, the hook nudge; the canary matrix over a full ingest, API, search, export, backup, CLI and MCP run; the terminal sanitiser on hostile fixtures; the subprocess rules; the logger allow-list; the read-only properties of the MCP server (closed tool list, read-only annotations, no path or URL argument, no network, no writes, transcript text only as marked untrusted data and only with `--include-text`). Expected codes are typed with the shared `ErrorCode` so a renamed code breaks the compile.
4. **Real settings are never read.** SEC-24 is redone with decoys: every process of the suite runs with `HOME`, `USERPROFILE`, `CLAUDE_CONFIG_DIR` and `MCS_HOME` in a temp root holding decoy `settings.json`, `settings.local.json` and `sessions/<pid>.key` files with canary content; the decoys must be byte-identical afterwards and the key decoy never opened; the installer's path resolver, called for every scope under that environment, returns paths inside the temp root only; a static check lists every production file that names `settings.json` and requires it to be the installer or its resolver. Release verification may compare names, sizes and modification times (a `stat`) of the real files, never their content.
5. **Resilience suite.** Platform neutral, no sleeps, faults injected at seams (the SQLite driver wrapper, the operations' own test seams) and never real disk exhaustion; kill points for `upgrade --yes` and `migrate-workspace --apply` prove the invariant "old or fully new, with a verified backup, and a rerun finishes"; the known limit of the transcript identity (a file rewritten in place with the same inode and the same first 256 bytes) is pinned by a test that names it. Thresholds are the budgets of the design (RSS delta, event-loop p99, bytes re-read).
6. **Flake policy** (from 05 4.7, kept): no retries; a failure without a code change is a defect; the only escape is a `QUARANTINE <date> <reason>` skip with a row in the quarantine table of `docs/testing.md`; the table must be empty at release for the layers above.
7. **Measurement.** The render cost of a 2,000-row transcript (O-2, budget 300 ms) is measured by a Playwright spec and written to a JSON result next to the run; a miss is a change request to the interface work, never a relaxed budget.
8. **CI and platforms.** The security, isolation and resilience projects run in `npm test` and therefore in the local `npm run ci` and in the Docker harness (there is no hosted CI, ADR 0078); macOS is verified by hand when a Mac is available; Playwright runs locally with the installed Chrome or a Chromium installed by the person running it (`MCS_PW_CHANNEL`).

## Consequences
- `axe-core` adds 3.4 MB to development installs and nothing to the shipped bundle. Its licence is MPL-2.0 (file-level copyleft: obligations apply to modified axe files, which we do not have). It is not redistributed, so the notices of the bundle (0063) do not list it; a test of the bundle checks that it is absent from the web assets.
- The suites cost time: the security and resilience projects start real processes; the whole `npm test` grows by minutes, and the release `stress` run triples the isolation, resilience and security part.
- Accessibility findings in interface code are fixed by the interface work, not by the test authors; a red a11y suite blocks the milestone, not the other suites.
- The decoy approach cannot prove that no code anywhere reads the real home; it proves that the code under test resolves everything from the environment, and the static check narrows where a settings path may be named.

## Alternatives rejected
- `@axe-core/playwright`: an extra package that pulls `axe-core` anyway; injecting `axe.min.js` from the installed package keeps one dependency.
- Lighthouse or pa11y: heavier, less precise rule control, and a second engine to pin.
- Hashing the real `settings.json` as V3 did: a read of a real settings file, forbidden by the rule for tests and agents (decision 13 of V4).
- Cross-stack tests in the server package: they would compile the web client without the DOM library and import across packages; the web package owns its client.
- Mocking the server in the browser tests: the V3 smoke found a missing API client only because it used a real instance.
- Retries for flaky browser tests: they hide ordering bugs; the policy forbids them.

## Evidence
- 2026-10-18 `npm view axe-core`: latest 4.14.0, published 2026-10-05; licence MPL-2.0; no dependencies; 3,430,531 bytes unpacked; previous releases 4.13.0 (2026-08-05), 4.12.1 (2026-06-10).
- The V3 browser smoke (`packages/web/e2e/specs/skeleton.spec.ts`) found the missing API client provider of the built app on its first run (LF-2, fixed by LF-6); the existing component and integration tests had not.
- The V3 designs: 05 sections 4.8-4.10, 5.3, 5.6 (the checklist ids SEC-01 to SEC-31) and 04 sections 11.2-11.4 are the source of the test lists; ADR 0073 decision 12 is the source of the responsive contract.
