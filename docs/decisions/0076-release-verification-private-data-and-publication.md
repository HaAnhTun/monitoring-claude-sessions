# 0076 Release verification for 4.0: the gates, private-data scans of the tree and the full history, clean-clone smoke, and publication from a clean history

Status: Proposed (V4, milestone M8, 2026-10-18). Owner: release area (F). Replaces the release-gate list G1-G10 of ADR 0056 (which the Python-removal ADR 0066 supersedes as a whole, because there is no legacy engine to cut over from); keeps its principle that no claim is made without a recorded run. Relates to 0065 (Docker harness; its GitHub Actions workflow and `ci-status` branch are dropped by 0078, CI is local only), 0061 (install paths), 0063 (bundle), 0075 (documents and licence).
Planned for a later 4.x release.

## Context
Owner decision 7: before the repository becomes public, the planning documents move out and the whole git history is scanned for personal data; if anything is found, a fresh-history branch is prepared for the owner to choose. Owner decision 3: a user machine needs only Node. The V3 definition of done (05 section 7.1) ran Python suites and legacy parity; it is obsolete. A read-only look at the repository on 2026-10-18 shows what the scan will find: all 85 commits carry one personal company e-mail address as author and committer, 32 ADR files contain scratch or workspace paths, and research notes were committed.

## Decision
1. **Definition of done for 4.0.** `release-check.mjs` runs the steps `git-clean`, `ci-strict` (`npm run ci -- --offline --strict --bundle`), `schemas-strict` (`schemas:check --no-pending`), `coverage`, `stress`, `slow`, `e2e`, `docs-check`, `check-text`, `check-docs --final`, `bundle-check`, `scan-tree`, `scan-history`, `clean-clone-smoke`, `plugin-install`, `docker-matrix` (opt-in), `audit-prod` and `install-reproducible` (opt-in), and writes a Markdown report outside the repository. Each row is `PASS`, `FAIL (exit n)` or `SKIPPED (<reason>)`; nothing is invented. A release is allowed only when every row except the opt-in rows is `PASS`, or `SKIPPED` for a reason the owner accepts in writing (a missing `claude` CLI on a build machine is the usual one). Platforms without a result are stated as unverified in the documents and the report.
2. **Private-data policy and tools.** The tree gate is `check-text` (in `npm run ci`): generic patterns for e-mail addresses, home paths of real users (placeholder names such as `x`, `me`, `user`, `fixture` are accepted), token shapes, long hex strings and Vietnamese letters outside the allowed paths. The release tool is `scan-private-data.mjs` (zero dependencies, `git` only): it scans the tree and, in history mode, the commit metadata (author and committer identities, messages, tag and branch names), every added line of every commit on every ref, and every path that ever existed, and reports the first commit that introduced each finding. Three inputs live outside the repository and are given by flag: a private blocklist (the owner's names, employer, handles and project roots; never printed, logged or committed), the NAMES (not the contents) of the sessions under the owner's Claude `projects` folder as a list of real session ids, and the allowed identities. A random-looking UUID without those inputs is a review item, not a finding.
3. **Publication from a clean history.** The published repository must not contain a finding. If the scan is not clean, which is certain at 8ca9475, publication uses a new repository whose history is new: one root commit with the final tree, or the final tree under a neutral root followed by the V4 commits rewritten with a neutral identity, or one commit per milestone. The old repository is renamed and stays private as the archive. The existing `main` is never force-pushed and no remote history is rewritten in place. The new branch must pass the same scan with exit 0 and have a tree identical to `main`. The identity is the owner's choice (a noreply address of the account or a project identity). Details and commands are in the release steps of the plan; they are git writes and belong to the lead.
4. **Clean-clone smoke.** `clean-clone-smoke.mjs` clones the repository at a ref (or uses an exported tree), uses the skill in three layouts (the checkout, the output of `install.mjs`, a simulated plugin cache with a versioned path and a space in a folder name) and drives the launcher through version, init, start, verify, status, doctor, a hook-stub probe, the served web index and stop. The environment cannot reach `npm`, `npx`, Python or a compiler: the PATH is rebuilt without any directory that holds them, shims of those names sit first and record any call, and the run fails if one is called, if a `node_modules` folder appears, if a process or an open port remains. It runs on this machine (Windows), and in the Docker harness of 0065 (`--smoke`: Linux x64 and arm64 emulated, glibc and musl, Node 22, 24, 26, an old-Node floor target). There is no hosted run (0078): macOS, Windows arm64 and the other platforms without a local result are stated as unverified until someone runs the smoke by hand.
5. **Plugin install test.** `plugin-flow.mjs` runs the `claude plugin` commands against a temp `CLAUDE_CONFIG_DIR`: `validate --strict` of the repository, the manifest and the skill folder, `marketplace add <path>`, `install`, `list --json`, a content and size check of the cache folder, the lifecycle through the installed launcher, `details`, `uninstall`, and a `stat`-only comparison of the real `~/.claude` files before and after. If `claude` is missing or has no `plugin` command, the script exits 77 and the report says `SKIPPED`.
6. **Reports.** The release report and the scan JSON are written outside the repository, in a private folder of the maintainer. The CHANGELOG states what was and was not verified; anything without a command result is labelled UNVERIFIED.
7. **Order after the code is done.** Documents are written and checked; the planning documents are archived; the text gate, the documents gate and the scans pass; the bundle is regenerated and checked; the release report is produced on the final head; the owner reviews the Vietnamese README and approves the publication route; only then the lead merges into `main` and pushes it to the private origin, and the owner publishes.

## Consequences
- The public repository starts with a new history; blame and per-commit history of the V3 and V4 build stay in the private archive.
- A scan depends on private inputs the repository cannot hold; the tool refuses to guess and says which input was missing.
- The smoke proves "needs only Node" on each platform it reaches, but not on a machine with an unusual Node build, a locked-down PowerShell or a read-only home.

## Alternatives rejected
- Trust a clean-looking tree and flip the existing repository: the history holds a personal e-mail address on every commit.
- Rewrite history in place with `git filter-branch` or a Python tool and force-push: a destructive shared-history operation, a Python dependency the project removed (0066), and it leaves the old objects reachable through caches and forks of a repository that was private.
- External scanners (gitleaks, trufflehog) as the gate: not Node-only, they know nothing about the owner's names, and their rule sets change; they may still be run by the owner as a second opinion.
- Run the smoke only in Docker: it would not cover Windows, which is the owner's machine.
- Test the plugin with a mock only: the mock is used for the unit test, but the contract with the product is the `claude plugin` command line, so the release step runs it for real.

## Evidence
- 2026-10-18 read-only: `git log` identity count (85 commits, one identity), `git grep` counts of scratch paths and archived-document citations, `claude plugin --help` and the help of `validate`, `marketplace add`, `install`, `uninstall`, `list` (all non-interactive with `--json`, scopes user, project, local), the plugin probe of the platform area (`plugin-probe`: marketplace add and install from a path under a temp config folder), the harness description in 0065.
- The V3 text gate and checklist (05 5.3 S-LOG-5, 7.1) as the starting point of the pattern list.
